Step-by-step guide

Deploy Azure Service Availability

One command in Azure Cloud Shell builds the whole backend in your subscription: two Azure Functions apps on the Flex Consumption plan, Azure Managed Redis, a locked-down storage account, private networking and monitoring. Then GitHub Pages publishes the dashboard.

Azure Cloud Shell (Bash) Bicep Managed identities, no secrets in the repo Tested end to end on 18 Nov 2026 · Indonesia Central
Start the deployment Why a storage account? See the architecture

Your values

Type your own values and every command on this page updates. Nothing leaves your browser. The defaults are the reference deployment.

Dashboard URL: https://ibranibeny.github.io/azure-service-availability/

Before you start

  • Rights in the Azure subscription. You create resources and role assignments, including Reader for the collector on the whole subscription. Your account needs Microsoft.Authorization/roleAssignments/write at subscription scope: for example Owner, or Contributor plus User Access Administrator or Role Based Access Control Administrator. Learn ↗
  • App registrations in Microsoft Entra ID. By default every user can register applications. If your tenant turned that off, you need the Application Developer role. Learn ↗
  • A region with Flex Consumption and Azure Managed Redis. The dashboard's Service matrix shows both. Everything goes into one region; Learn recommends keeping the function app's storage account in the app's region. Learn ↗
  • Azure Cloud Shell (Bash). It includes the Azure CLI and Bicep. Sessions end after 20 minutes without interaction, and ephemeral sessions keep no files, but the Azure deployment keeps running and you can resume it (Troubleshooting). Building the packages needs Python 3.12, the apps' runtime; scripts/build.sh checks and stops otherwise. Cloud Shell had 3.12.15 on 18 Nov 2026; if yours differs, point PYTHON to a 3.12 interpreter. Learn ↗ · tools ↗
  • A GitHub account. With GitHub Free, Pages needs a public repository. Pages sites are public on the internet even when the repository is private, which is fine here: the site and config.js hold public identifiers only, no secrets. GitHub Docs ↗
  • Resource providers. The script registers any that are missing: Microsoft.App (Learn requires it for Flex Consumption VNet integration), Microsoft.Web, Microsoft.Cache, Microsoft.Network, Microsoft.Storage, Microsoft.Insights, Microsoft.OperationalInsights, Microsoft.ManagedIdentity. Learn ↗

Reruns apply whatever settings they get. Export your values once per Cloud Shell session (Step 2 does) so a later run doesn't fall back to the defaults.

1 Get the code

  1. Fork ibranibeny/azure-service-availability into your GitHub account.
  2. Open Azure Cloud Shell, choose Bash, and check that you're in the right subscription: 
    az account show --query "{subscription:name, user:user.name, tenant:tenantId}" -o table
# only if it's the wrong one:
az account set --subscription "<subscription name or ID>"
  3. Clone your fork: 
    git clone https://github.com/ibranibeny/azure-service-availability.git
cd azure-service-availability

2 Deploy

export PAGES_URL=https://ibranibeny.github.io/azure-service-availability/
export ALLOWED_DOMAINS=contoso.day
export LOCATION=indonesiacentral
export RG=rg-azure-service-availability
bash scripts/deploy.sh 2>&1 | tee ~/deploy.log

The script prints a heading for each phase. This is what each one does:

HeadingWhat happens
==> Signed-in account and subscriptionShows where it will deploy. Press Ctrl+C now if that's the wrong subscription.
==> Resource providersRegisters the providers that aren't registered yet.
==> Microsoft Entra app registrations (API + dashboard)scripts/entra-apps.sh creates or updates the API app (scope Availability.Read, v2 tokens) and the dashboard app (single-page app, redirect URIs PAGES_URL and http://localhost:8080/, pre-authorized for the API). It tries to grant admin consent and prints both app IDs.
==> Infrastructure in …Creates the resource group, starts infra/main.bicep as deployment asa-<UTC time> without waiting for it, and prints the command to resume if Cloud Shell disconnects.
==> Build Function apps in the backgroundWhile Azure deploys, builds both zip packages locally with Python 3.12: the collector (52 MB, it carries the Azure CLI) and the API (7 MB).
==> Infrastructure deployment in …Checks every 30 seconds until the deployment succeeds. If it fails, it prints each failed resource with its error. The API app waits for the collector because both join snet-functions. A rerun on 18 Nov 2026 finished in under 2 minutes; a first run takes longer.
==> Deploy the Function app codeaz functionapp deployment source config-zip --build-remote false for each app, up to 3 tries. The package lands in the app's own blob container. Learn ↗
==> First collectionRuns the timer function once through the collector's admin endpoint; HTTP 202 means accepted. After that the schedule takes over. Learn ↗
==> Dashboard settings for docs/config.jsPrints the values for the dashboard. They're public identifiers, not secrets.

Differs from Learn's default. For Python, Learn says to request a remote build (--build-remote true), mainly to avoid packages built on Windows for Linux. This project builds on Linux in Cloud Shell instead: build.sh insists on Python 3.12 and stops if a compiled package needs a newer Linux than the Functions image. That worked in the reference run. A remote build wasn't tested with this private-storage setup. Learn ↗

3 Publish the dashboard

  1. Put the printed block into docs/config.js in your fork. On GitHub: open docs/config.js, select Edit, replace the content and Commit changes.
  2. Turn on GitHub Pages: Settings › Pages › Build and deployment › Source: Deploy from a branch, branch main, folder /docs, then Save. The folder has a .nojekyll file, so GitHub serves the files as they are. Changes can take up to 10 minutes to appear. GitHub Docs ↗
  3. Open https://ibranibeny.github.io/azure-service-availability/. You land in the guest view; Sign in uses your Entra tenant.

If the dashboard ends up at a different URL than PAGES_URL (a custom domain or a renamed repository), run PAGES_URL=<real URL> APPS=none bash scripts/deploy.sh so the redirect URI and CORS match. Otherwise sign-in and API calls fail.

4 Check it works

In the same Cloud Shell folder:

API=$(jq -r .apiBaseUrl.value .deploy/outputs.json)
curl -s "$API/health"                                                    # {"status":"ok"}
curl -s -o /dev/null -w '%{http_code}\n' "$API/summary"                  # 200 with the guest view on, 401 when it's off
curl -s -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer x.y.z' "$API/summary"   # 401: a bad token is refused, never treated as a guest

Then confirm the first collection in Application Insights. The first query installs the log-analytics CLI extension (preview).

WS=$(az monitor log-analytics workspace list -g "$RG" --query "[0].customerId" -o tsv)
az monitor log-analytics query -w "$WS" -o table --analytics-query \
  "AppTraces | where Message startswith 'Collection finished' | project TimeGenerated, Message | order by TimeGenerated desc | take 3"

In the reference run it logged:

Collection finished: {"at": "<time of the run, UTC>", "durationSec": 88.5, "regions": 65, "vmRows": 67469, "azCalls": 75, "errors": 0}

Finally, look at the storage account from the management plane. The script only lists names and settings; it never reads blob, queue or table contents:

bash scripts/inspect-storage.sh             # add --timings for deployment history and the slowest resources

It should show public network access Disabled, allowSharedKeyAccess: false, private endpoints for blob, queue and table, the two package containers next to the containers the Functions host creates, and the role assignments of both identities. On the dashboard, Schedule & changes lists the run and the time of the next one.

Why a storage account?

Because Azure Functions needs one to run. Every function app is tied to a general-purpose storage account, its host storage, set in the AzureWebJobsStorage connection, and the app can't start without it. The Functions runtime keeps its own working state there, and on the Flex Consumption plan the deployed code lives there too. The dashboard's data isn't in it: that's in Azure Managed Redis. Learn ↗

Why not keep everything in Redis?

They hold different things. Redis holds what the dashboard reads, written by our code. The storage account holds what the Functions platform needs to run the apps: their code, the timer coordination and their keys. Azure Functions requires a storage account that supports blob, queue and table storage for this, so it can't be replaced with Redis. Learn ↗

How it's locked down, and why

Identities instead of keys

Host storage uses an identity-based connection: AzureWebJobsStorage__accountName, __credential=managedidentity and __clientId of each app's user-assigned identity. The package containers use UserAssignedIdentity authentication. Shared key access is disabled on the account (allowSharedKeyAccess: false), so no account key or SAS signed with it works at all. Learn describes managed identities as the highest level of security for connecting to Azure resources ↗, and Flex Consumption supports them fully for host storage ↗. Learn's infrastructure-as-code guidance also recommends turning shared key access off ↗.

Least-privilege roles

Storage Blob Data Owner is the minimum for host storage and covers the timer lock and the package container (which needs at least Storage Blob Data Contributor). Storage Table Data Contributor lets the host write diagnostic events. Storage Queue Data Contributor is also assigned, though these timer and HTTP functions don't need it (queues serve blob triggers, Durable Functions and retries). Removing it would tighten access further; that wasn't tested here. Learn ↗

Private network only

Public network access is disabled. The apps reach blob, queue and table through private endpoints in snet-private-endpoints, and the privatelink.blob/queue/table.core.windows.net zones are linked to the VNet so the names resolve to private IPs. Flex Consumption sends all outbound traffic through VNet integration, and it's the dynamic plan Learn points to for secured storage accounts with managed identities. The trade-off: you can't browse the contents from the portal or Cloud Shell, only from inside the VNet. Settings and container lists still work through Azure Resource Manager. Learn ↗

One account for both apps, same region

Learn allows apps to share a storage account and recommends a separate account per app for performance; on Flex Consumption the apps' host IDs don't collide. These two apps are light (a timer every 6 hours and a small read-only API), so one account means 3 private endpoints instead of 6. Split it if the load grows. The account is in the apps' region, as Learn recommends. Learn ↗

Tested, not spelled out on Learn. Package deployment and app startup worked with the storage account's public network access disabled in the reference run on 18 Nov 2026. Learn covers secured storage and Flex package deployment separately but doesn't describe this exact path, so rerun Step 4 after you change the network or storage settings.

Look after this account: Learn points out that it holds function code, access keys and other service data, so limit who can reach it and monitor both control-plane activity (for example listing keys) and data-plane operations. Learn ↗

Clean up

The resources keep costing money while they exist (Azure Managed Redis is billed by the hour), so delete everything when you're done. Remove the subscription-level Reader assignment first: deleting the resource group doesn't remove assignments made at subscription scope.

RG=rg-azure-service-availability
SUB=$(az account show --query id -o tsv)
PRINCIPAL=$(az identity list -g "$RG" --query "[?contains(name, 'collector')].principalId" -o tsv)
az role assignment delete --assignee "$PRINCIPAL" --role Reader --scope "/subscriptions/$SUB"
az group delete -n "$RG" --yes --no-wait
for N in "Azure Service Availability Dashboard" "Azure Service Availability API"; do
  az ad app delete --id "$(az ad app list --display-name "$N" --query "[0].appId" -o tsv)"
done

On GitHub, set Settings › Pages › Branch to None and save, or delete the fork.
